# hot-open 判据修正 + 「5MB 比 10MB 慢」的根因：大文件模式阈值悬崖（2026-09-25）

**结论**：`2026-09-25-perf-hot-open-authoritative.md` §3.3 把「5MB 比 10MB 慢」记为
「不随尺寸单调 → 不得归因于大文件处理」。本轮定位到**真实机制**，该表述需要修正：

> **它是大文件模式（Large File Mode）的阈值悬崖，只不过方向是「更小的文档更慢」。**
> Mellow 的 `LARGE_FILE_BYTES_THRESHOLD = 5 × 1024 × 1024`，判定用**严格大于**；
> 而夹具 `5MB.md` 的字节数**恰好等于** 5,242,880 → **不触发**大文件模式 →
> 对一篇 5MB 文档付**全量**渲染成本；`10MB.md` 触发降级路径（视口裁剪解析、
> 装饰数上限、关拼写、关动画）→ 反而更快。

---

## 一、先修判据：`switchMs` 原本测的不是「文档切换」

### 1.1 症状

尺寸扫描（1–10MiB）得到 `switchMs` **21–310ms 且与尺寸无关**，其中 8–10MiB 只有 21–33ms，
**比 1MiB 的 108ms 还快** —— 物理上不可能。说明它抓到的是**偶发重绘**
（工具条/滚动条/光标），不是文档内容呈现。

### 1.2 原因一：绝对阈值比真实信号低一个数量级

`pixelDiff` 返回「变化采样点数」，校准阈值 `max(calibMax*3, 60)`。
对一个 576×96 的 ROI（13,824 个采样点）而言 **60 只占 0.4%** —— 它只回答
「有没有像素动」，拦不住任何工具条重绘。

实测真实信号有多大（1MB → 5MB 切换）：**变化 730–1050 个采样点 = 5.3%–7.6%**。
即原阈值比真实信号低约 **12 倍**。

### 1.3 原因二（更根本）：帧几何不恒定，分母是错的

改成绝对点数阈值后出现**数学上不可能**的值：

```
sampleCount = 13824（取自 576×96 的帧）   实测 changed = 17372   ← changed > total
                                             另一轮 changed = 20547
```

`pixelDiff` 只取 `a` 的几何，且全仓假设「一个流生命周期内帧尺寸恒定」。
该假设**不成立**：SCK 在流启动初期可能先交付未套用 `config.width/height` 的帧。
于是任何「变化点数 ÷ 事先算好的采样点总数」都建立在错误的分母上。

**修法**：新增 `pixelDiffPair(a, b)`，按 `min(wA,wB) × min(hA,hB)/4` **逐对**计算总数，
并用**比例**阈值（`--switch-min-frac`，默认 **3%**）；同时把「基准帧与比较帧几何不一致」
的帧数计入 `switchDimMismatchFrames` 诊断字段，使该问题可见而非静默。

### 1.4 判据修正后的复测（同一扫描）

| 目标 | ok | switchMs | 实测变化（阈值 414） |
|---|---|---|---|
| ASCII 1MiB | 0/2 | FAIL | 15 |
| ASCII 5MiB | 0/2 | FAIL | 15 |
| ASCII 10MiB | 2/2 | 2321, 2317 | 1262, 1277 |
| repo 1MB.md | 2/2 | 2347, 2303 | 706 |
| repo **5MB.md** | 2/2 | **2917, 2872** | 1280, 1271 |
| repo 10MB.md | 2/2 | 2294, 2282 | 1277, 1277 |

> **ASCII 1MiB / 5MiB 的 FAIL 是扫描脚本自身的缺陷，不是被测对象的问题**：
> 我的纯 ASCII 夹具都由同一段重复文本生成，`base.md` 与 `a1.md` **字节完全相同**、
> 与 `a5.md` 共享同一前缀 → 切换后顶部带**没有任何变化**（实测变化 15），
> 判据正确地拒绝了它。故 ASCII 组**只 10MiB 是有效对照**。
> 这一条要记住：**扫描夹具若内容相同，测到的「切换」是假的。**

## 二、根因：5 MiB 阈值悬崖（方向反直觉）

### 2.1 代码证据

`packages/editor-engine/src/largeFile.ts`：

```ts
/** 字节阈值（5 MB） */
export const LARGE_FILE_BYTES_THRESHOLD = 5 * 1024 * 1024;
/** 行数阈值（50,000） */
export const LARGE_FILE_LINES_THRESHOLD = 50_000;

/** 触发判定（纯函数，可单测）：超过任一阈值即进入大文件模式 */
export function classifyLargeFile(byteLength: number, lineCount: number): boolean {
  return byteLength > LARGE_FILE_BYTES_THRESHOLD || lineCount > LARGE_FILE_LINES_THRESHOLD;
}
```

进入大文件模式后自动降级（该文件头部注释）：offscreen Mermaid/Math 裁剪到视口 ± 余量、
image lazy、spellcheck off、heavy decorations 上限、animation off。

### 2.2 与夹具的对应关系

| 夹具 | 字节 | 行数 | 字节 > 5MiB | 行数 > 50k | 大文件模式 |
|---|---|---|---|---|---|
| `1MB.md` | 1,048,576 | 8,165 | ✗ | ✗ | 否 |
| **`5MB.md`** | **5,242,880** | 40,015 | **✗（恰好相等）** | ✗ | **否** |
| `10MB.md` | 10,485,760 | 79,971 | ✓ | ✓ | **是** |

`5,242,880 === 5 × 1024 × 1024` —— 夹具**正好压在阈值上**，而判据是**严格大于**，
于是它落在「付全量成本」的那一侧。这解释了 `switchMs` 的排序：
**5MB（2917ms，全量）> 10MB（2294ms，降级）≈ 1MB（2347ms，小）**。

注意 `run-benchmark.mjs` 的 `modeMap` 早就把 `5MB.md` 标为「边界」——
本轮把「边界」具体化成了「**恰好等于大文件模式字节阈值**」。

### 2.3 需要裁决（未擅自改动）

1. **阈值语义**：`>` 还是 `>=`？`5MB.md` 恰好落在边界上，使得「5MB 是边界样本」
   实际测的是「未降级的最坏情况」。若产品意图是「≥5MB 即降级」，应改 `>=`。
2. **夹具**：`5MB.md` 是否应改为略大于 5 MiB（例如 5.5MB），
   以免一个「边界」样本同时承担「未降级」与「大文件」两种语义？
3. 这是**产品行为**（PRD §109），不是 harness 问题，故本环境只记录、不改。

## 三、结论（对前一份文档的更正）

- 前文「`switchMs` 不随尺寸单调 → 不得归因于大文件处理」**修正为**：
  **确实存在大文件模式阈值效应，但方向是「恰好未触发降级的 5MB 最慢」**。
- 前文「hot-open 首组读数 2970/2288ms」的**数值本身可信**（与修正判据后的
  2917/2294ms 吻合），但其当时的判据（绝对阈值 60）不足以支撑结论。
- `switchMs` 现在有了经校验的判据（帧对比例 ≥3%），且把「帧几何不一致」计入诊断。

## 四、仍未解决

1. `switchMs` 仍只能测「顶部带首次实质变化」，与「文档可编辑」不是同一件事
   （`echoMs` 才接近后者）；两者相加的口径是否合理，需在 spec 层面确认。
2. 扫描夹具需改为**内容可区分**（当前纯 ASCII 组只有 10MiB 有效）。
3. 阈值语义 / 夹具尺寸的两项裁决（§2.3）。
