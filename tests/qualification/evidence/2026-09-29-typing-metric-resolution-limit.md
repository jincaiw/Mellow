# typing 指标：量具分辨率低于 PRD 目标（2026-09-29）

## 一、先修的两处缺陷

### 1.1 `typing` 在报告里**没有章节标题**

报告的小节序列是 `1. startup` → `2. open-to-editable` → `4. scroll` → `5. search` …
**`## 3.` 整段缺失**：typing 表格被直接追加在 §2 之后，视觉上被读成「第 2 节的一部分」。
已补 `## 3. typing（逐键回显延迟，ms）`。

### 1.2 校准噪声可以让该指标**完全失效**

实测出现过：

```
typing: p95=146.41ms median=146.41ms timeouts=9
```

根因不是按键没进去，而是**校准抓到了非按键变化**：

- 实测 `calibMaxDiff = 112`（校准窗口内窗口有变化，疑为光标闪烁等）
- 旧判据 `threshold = max(calibMax * 3, 60) = 336`
- 而「插入一个字符」的信号只有约 **59** 个采样点
- → 336 ≫ 59，**每一个按键都被判为「未回显」** → `latencies` 全是 -1，
  P95 被污染（`timeouts=9` 说明触发了连续超时快速失败）

这与 `open` 指标暴露的是同一个坑（绝对阈值 + 魔法地板），修法也一致：
改用比例判据 `ECHO_MIN_FRAC = 0.001`。修后实测 **12/12 有效、0 超时**，
且三种配置都稳定（带点击 / `--no-click` / 全高 ROI）：
`latencies = [143,132,142,119,127,104,111,108,103,116,93,102]`（带点击）。

## 二、更根本的问题：**量具分辨率低于 PRD 目标**

`typing` 的判据是**屏幕捕获的首帧变化**，采样率由 SCK 帧率决定：

```
detectFrames = 459 / 8000ms  →  ≈57fps  →  单帧 ≈ 17.4ms
```

而 PRD §110 对普通文档的目标是：

```
P95 update < 16ms
```

**16ms < 17.4ms —— 目标低于量具的分辨率下限。** 因此：

1. 观测到的 ~100ms 主要来自「**合成事件 → 渲染 → 屏幕捕获**」管线的固定延迟，
   **不是**编辑器自身的更新耗时；
2. 「达标 / 未达标」在此口径下**不可判定**。

### 修法：不给不可支撑的结论

报告原先把 `mt.p95 < 16` 直接渲染成 ✅/❌ —— 一个 100ms 的观测会被读成「未达标 6 倍」。
现改为：目标低于量具分辨率时输出 **「不可判定（低于分辨率）」**，不输出 ✅/❌。
高于分辨率的目标（Large 的 32ms）仍正常判定。

### 实测（2026-09-29）

| fixture | 模式 | Mellow P95 | 目标 | 判定 |
|---|---|---|---|---|
| 1MB.md | 普通 | 102.48ms | <16ms | **不可判定（低于分辨率）** |
| 5MB.md | 边界 | **380.51ms** | <32ms | **❌**（32ms 高于分辨率，判定成立） |

> `5MB.md` 的 380.51ms 比 `1MB.md` 的 102.48ms 慢 3.7×，且 `5MB.md` **恰好压在
> 大文件模式阈值上（不降级）** —— 与 09-25 定位的「5MB 是最坏情况」一致。
> 但两值都含管线固定延迟，**只能读差值量级，不能读绝对值**。

## 三、剩余风险（未解决）

**屏幕差分区分「插入一个字符」与「其他重绘」的余量很薄**：
信号约 59 个采样点，而观测到的校准噪声最高到 112 个采样点。
即噪声可以**大于**信号 —— 单靠幅度阈值无法可靠分离。当前的比例判据（0.1%）低于二者，
故存在**误报**可能（把某次重绘当成回显 → 低估延迟）。

要判定 PRD §110 的 16ms 目标，必须换测量方法：

1. 应用内 `input → paint` 埋点（在编辑器里直接测，绕开屏幕捕获）；
2. CDP tracing / `PerformanceObserver` 取 `event` 到 `paint` 的间隔。

护栏：`run-benchmark` 必须声明 `SCK_FRAME_MS`、必须输出「分辨率限制」段落、
目标低于分辨率时必须输出「不可判定（低于分辨率）」、必须实际计算 `belowResolution`。
注入验证（**全局**替换，否则只改到第一处、护栏仍通过）：→ 护栏报错；还原 → 通过。

# 附：startup 指标首次取得读数（同日）

PRD §110 的 **Startup 目标（P95 ≤ 1.2s to editable）此前从未测过** —— 它是唯一没有数据的
PRD 性能目标。本轮补测（`--app both --metrics startup --runs 5 --warmup 1`，同机同会话）：

| app | median | p95 | min | max | n |
|---|---|---|---|---|---|
| Typora 1.14.9 | 452.7 | 461.1 | 406.1 | 461.1 | 5 |
| **Mellow** | **317.5** | **321.9** | 300.8 | 321.9 | 5 |

- **同机对照：Mellow/Typora P95 比值 = 0.70×（Mellow 快约 30%）**
- **PRD 判定：Mellow ✅ 达标（321.9ms ≤ 1200ms）；Typora ✅ 达标（461.1ms）**
- 分辨率说明：该目标（1200ms）远高于量具分辨率（单帧 ≈17.4ms），**判定成立**
  —— 与 typing 的 16ms 目标（低于分辨率、不可判定）形成对照。

这是目前**唯一一个「双侧都达标且 Mellow 更快」的 PRD §110 目标**。
报告 §1 原先只打印表格与目标文本、没有比值与判定，本轮补上（含分辨率说明）。

## 附带修掉一个**静默** bug：`results[].app` 的键名大小写

`results[].app` 的取值是 `'Mellow'` / `'Typora'`（**首字母大写**）。
用小写查询会**静默**返回 `undefined` —— 不报错、不输出，只是整段报告消失。
实测踩过两次：

- typing 的「逐样本诊断」段；
- startup 的判定段（首次重跑时输出「缺少一侧读数，无法给出同机对照比值与判定」，
  而表格里两侧数据都在 —— 这个自相矛盾才暴露了它）。

护栏：禁止 `x.app === 'mellow' | 'typora'`，并要求按大写字面量调用查询 helper。
注入验证：改小写 → 护栏报 2 条错；还原 → 通过。

## 附带精确化一条既有护栏（不是绕开它）

既有的「不得直接把 Typora 的 median/p95 当分母」反例锁会命中 startup 节的比值。
但该锁的立据是「**超限夹具**的 Typora 侧是提示页耗时」—— 而 **startup 没有夹具**
（blank 冷启动），故该节内的直接比值合法。

处置：把 startup 节从扫描范围中**排除并写明理由**，而不是改变量名绕开
（改名绕开会腐蚀护栏本身，比误报更糟）。并加一条断言验证切片确实生效
（`rawRatioScan` 必须仍含 `## 3. typing`），否则护栏会**静默失效**。
注入验证：在 typing 节插入裸相除 `mt?.p95 / ts?.p95` → 原护栏仍报错（例外未废掉原锁）。
