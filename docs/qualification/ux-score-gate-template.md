## 二、30 个核心 Typora 任务效率 Gate（PRD §132）

> **清单归属说明（2026-09-30 补，防止误引宪法）**：
> **PRD §132 不含任务清单** —— 该节原文只有「30 个核心 Typora 任务：」+ 四条阈值。
> 下方 30 项**由本模板定义**（master plan §9.5 指定本模板为唯一来源），
> 故**逐项内容属方法论，可修正**；而 §132 规定的**数量（30）与阈值（+5% / +15% / 错误率 / IME / data loss）不可改**。
> 另：PRD 侧把 10MB 定为必须执行的是 **§129 J18**（「必须全部通过」），与本 Gate 的第 30 项是**两件事**——
> 前者是**能力/旅程**要求（只评 Mellow 绝对表现），后者是**效率对照**要求（需 Typora 可比）。
> 引用时勿把两者混为一谈（此前审计与 ADR-0025 曾误写成「PRD §132 任务清单第 17 项」）。

### 执行方法
1. 同一台机器、同一份测试文档：**已指定为 `tests/fixtures/ux-gate/`**
   （主文档 `ux-gate-30tasks.md`；先把整个目录复制到工作目录再测，见其 `README.md`）。
   Typora 1.14.9 与 Mellow 各做一遍；
2. 每任务记录：完成时间（秒）、错误（0/1）、步骤数、主观评分（1-5）；
3. 换顺序再做一轮（消除熟练度偏差），取均值；
4. 要求：≥90% 任务完成时间 ≤ Typora+5%；任一关键任务不慢 >15%；错误率不高于 Typora；IME corruption=0；data loss=0。

> **为什么把文档固化（2026-09-30 补）**：本节原写「同一份测试文档（`tests/fixtures/`）」——
> 但**没有任何文档被指定**。而 30 项里一半以上依赖特定内容（`[TOC]`、脚注、公式、
> **一处故意写错的 Mermaid**、可写入的 `assets/`、带对齐的表格、四级标题、可被外部修改的文件）。
> 不指定 → **三场平台会话各用各的文档**，任务内容不可比，「修正错误 / 加一行」也无从复现。
> 现固化为 `tests/fixtures/ux-gate/`，并由护栏断言其内容不变量（删掉某项能力会让
> 对应任务**无法执行** → 在人工会话里表现为「跳过」→ 变成**静默缺失的观测**）。

会话开始时**自己生成**记录（不要把草稿文件提交进仓库 —— 见下方说明）：

```bash
# ① 记下本次要验收的修订
git rev-parse --short HEAD

# ② 生成记录：已预置 120 条观测骨架（task/app/round 已生成、appOrder 已按交替规则算好，
#    且不含任何测量值），你只需补测量值（durationMs / error / steps / subjectiveScore /
#    evidence / entryPoint / sourceDiff），不要改结构。
#    落点目录由 init 自建，无需预先创建。
node tests/qualification/ux-gate-recorder.mjs init \
  --output docs/qualification/evidence/macos-ux-gate-<date>.json \
  --platform macos --commit <①的 sha>
```

```bash
# ③ 中途随时查看进度（只读，不判定、不因未填完而失败）
node tests/qualification/ux-gate-recorder.mjs progress \
  --input docs/qualification/evidence/macos-ux-gate-<date>.json

# ④ 120 条填完后校验（计算 PRD §132 的 +5% / 关键任务 +15% / 错误率 / 主观评分 Gate）
node tests/qualification/ux-gate-recorder.mjs validate \
  --input docs/qualification/evidence/macos-ux-gate-<date>.json
```

`progress` 会报告：已填写完整条数、字段不完整的条目（指明缺哪个字段）、未填条目、
**appOrder 交替规则**（同一轮内 typora/mellow 顺序必须一致；两轮之间必须交换），
以及 **`mellowCommit` 与当前 HEAD 是否一致**（不一致会明确警告 —— 这直接决定
「这份证据对应哪个构建」）。
`validate` 要求 30 × 2 app × 2 round 共 120 条记录、每任务两轮交换 app 顺序、
截图/视频/日志证据、IME/data-loss 明确为零；并会回传 `commitNote` 供人工核对
（**不一致不判失败**：校验可能晚于会话，期间有新提交落地；失败会逼人改成
「看起来对」的 sha，反而更糟）。

> **为什么不再提交一份预生成的 `DRAFT` 记录（2026-09-30）**：
> 仓库里曾有一份 `docs/qualification/evidence/macos-ux-gate-DRAFT.json`，其真实作用是
> **让 git 保留 `docs/qualification/evidence/` 这个空目录** —— 因为 `init` 当时不创建落点目录。
> 但那份草稿里的 `mellowCommit` **在下一个提交就过期**（实测：草稿写 `c2ba524`，
> 两小时后 HEAD 已是别的提交）。人工若照草稿填，记录就会指向**没被测过的修订**。
> 现 `init` 自建目录，草稿不再需要 —— 且**不得**再提交带 commit 的草稿
> （护栏已锁：`docs/qualification/evidence/` 下不得存在预生成的草稿记录）。

## 三、执行前必读：两项已知障碍

### 3.1 任务 30：对照尺寸改为 ≈2 MB，>2 MB 单列为**非对照能力观察**（ADR-0025 Q3a = C1，已裁决 2026-09-30）

**事实（一级证据）**：**Typora 1.14.9 不渲染超过 2,000,000 字符的文档** ——
它对 10 MB 只显示「该文件过大，因此无法在 Typora 中呈现」提示页，既不渲染也不可编辑。
一级证据：`TypeMark/appsrc/window/frame.js` 的 `tryEnterOversize` 判定
`e.length > File.MAX_FILE_SIZE`，同文件 `MAX_FILE_SIZE: 2e6`；实测边界
1,900,000 字符正常渲染 / 2,100,000 字符为提示页。
详见 `tests/qualification/evidence/2026-09-23-typora-render-limit-2mb.md`。

**裁决（ADR-0025 Q3a = C1）**：

- **任务 30 的对照尺寸改为 ≈2 MB**（Typora 可渲染上限内）→ 该任务恢复「同尺寸对照」的可比性；
- **>2 MB（含 10 MB）单列为「非对照能力观察」**：只记 Mellow 的**绝对**指标
  （能否打开 / 搜索 / 编辑 / 保存），Typora 侧记「不适用」并附上面的原因。
  这一条**不是**效率对照，**不进** 120 条计时记录。

> **为什么这不是「降低要求」**：PRD §129 J18 要求「10 MB 文档仍然可编辑」——
> 该能力由「非对照能力观察」承接，仍要被观察到；变的只是**它不再伪装成对照**。
> **禁止**在 Typora 侧为该尺寸编造任何数据（本门禁明令禁止伪造计时）。

**层级区分（勿互相顶替）**：本节属**模板层**修正（30 项清单由本模板定义，
PRD §132 未规定夹具尺寸）。而 **PRD §129 J18 × §110「必须同机型与 Typora 对照」**
的冲突是**宪法层**（ADR-0025 Q3b）—— 改掉第 30 项**并不能**让 J18 在 Typora 侧变得可执行。

**>2 MB 能力观察怎么记**：写进最终记录的 `notes` 字段（或本模板附页），至少包含：
① 夹具（`tests/benchmark/fixtures/10MB.md`，由 `cd tests/benchmark && node generate-fixtures.mjs` 生成）；
② Mellow 侧四项动作（打开 / 搜索 / 编辑 / 保存）是否完成；
③ Typora 侧「不适用」+ 本节的一级证据原因。

### 3.2 环境前置

- **输入源须为键盘布局（如 ABC）**：IME 类任务另需按 `docs/specs/ime-test-plan.md`
  准备中文/日文输入源；若会话中途输入源被切成 IME，非 IME 任务的耗时会被候选窗干扰。
- **屏幕不得锁定/屏保**：锁定状态下任何应用都无法成为前台，截图与「外部修改重载」
  一类任务会得到静止画面。
- **同一台机器、同一份文档**：对照必须在同机同文档下进行（PRD §132）——
  文档已固化为 `tests/fixtures/ux-gate/`，请勿临时改用别的文档。

## 四、证据要求

> ⚠️ **以验证器的要求为准**（2026-09-30 对齐）：`ux-gate-recorder.mjs validate` 要求
> **每一条观测**（30 任务 × 2 应用 × 2 轮 = **120 条**）都带至少一项证据
