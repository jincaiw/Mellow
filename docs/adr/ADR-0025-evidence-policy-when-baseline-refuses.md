# ADR-0025 — 基线产品拒绝执行时的证据政策（Typora >2MB 拒渲染）

**Status:** **Accepted**（2026-09-30）—— 已裁决并生效（原 Proposed 2026-09-29）

## 裁决（2026-09-30）

> 依据：用户于 2026-09-30 授权「全部自行评估、决策、实施」。**授权不等于降低举证标准** ——
> 三问均采纳本 ADR 起草时的建议（A1 / B1 / C1），理由如下，无偏离。

### Q1 = **A1**（更正为限定式）

合同文本**不应包含已知为假的陈述**：现文本「同机、同文档条件下维持可编辑和可导航。」
对 >2MB 为假（Typora 根本不渲染）。限定式表述既不削弱 Mellow 的义务，
也不留下可被误引的假事实。

**已实施**：台账 `P0-PERF-001.typoraBehavior` 改为
「同机、同文档条件下维持可编辑和可导航；**Typora 自身对 >2,000,000 字符的文档不渲染，
该尺寸无 Typora 行为可比**（一级证据：`TypeMark/appsrc/window/frame.js` 的
`tryEnterOversize` + `MAX_FILE_SIZE: 2e6`）」。

### Q2 = **B1**（保留夹具，Typora 列记「不适用」）

`ratioOrNA()` 与报告的「有效样本与探针失败率」标注已把风险控制住（**已核实该函数存在**：
`run-benchmark.mjs` 的 `ratioOrNA`，跨应用比值一律经它判定基线有效性），改动最小。
B3（引入第三方基线）超出 PRD §110「与 Typora 对照」的规定，不采纳。

### Q3 = **C1**（任务 30 对照尺寸改 ≤2 MB + >2 MB 单列为非对照观察）

**已实施**：
- `ux-score-gate-template.md` §二任务表第 30 行 → 「大文档（**≈2 MB**，Typora 可渲染上限内）打开 → 搜索 → 编辑 → 保存」；
- `ux-gate-recorder.mjs` 的 `TASKS[29]` 同步改为「大文档（≈2 MB）打开、搜索、编辑、保存」；
- 模板 §3.1 重写为「对照尺寸 ≈2 MB + >2 MB **非对照能力观察**」；
- 夹具文档 `tests/fixtures/ux-gate/ux-gate-30tasks.md` 同步；
- 护栏 `verify-parity-ledger.mjs`：末项断言由「含 10MB」改为「**含 ≈2 MB**」，
  并新增「模板必须保留『>2 MB 非对照能力观察』」断言 ——
  防止有人把对照尺寸改回 10 MB（那会逼人编造 Typora 数据），
  也防止「非对照观察」随尺寸调整而**静默消失**（那会让 PRD §129 J18 的能力要求失去承接）。

### Q3b（宪法层）：**澄清后不存在真实冲突**

原表述把 **PRD §129 J18（能力）** 与 **§110（测量规则）** 当作互相冲突的两条。
逐条读原文后可判定：二者**管的是不同的事** ——

- §129 J18「10 MB 文档仍然可编辑」是**能力要求**：由「非对照能力观察」承接（Mellow 侧绝对事实）；
- §110 规定的是**性能目标的测量规则**（须与 Typora 同机对照）：它只适用于**基线能执行**的尺寸；
  对 >2MB，基线拒绝执行 → 该尺寸**不存在可比读数**（这正是 Q2=B1 的 `ratioOrNA` 分支）。

即：**不需要改宪法**，需要的是把「能力」与「对照」分开陈述。故 Q3b 以本节的读法结案。

> **本 ADR 不覆盖**：`P0-PERF-001` 的测量口径（1MB/10MB 目标按哪种口径判定）属 **ADR-0026**。

## 背景

### 事实一：Typora 1.14.9 不渲染超过 2,000,000 字符的文档（一级证据）

`TypeMark/appsrc/window/frame.js`：

```js
tryEnterOversize: function(e,t,n){ return (!File.isMac||File.bundle.filePath)
  && (a.bindOversizePlaceholder(), t || e.length > File.MAX_FILE_SIZE)
    ? (File.doEnterOversize(n), "") : (File.exitOversize(), e) }
// 同文件内：MAX_FILE_SIZE: 2e6
```

命中时只显示「The file is too large to render in Typora.」
（zh-Hans「该文件过大，因此无法在 Typora 中呈现」）提示页 + 一个 QuickLook 按钮，
**既不渲染也不可编辑**。实测边界：1,900,000 字符正常渲染 / 2,100,000 字符为提示页。

### 事实二：这与 PRD 的验收设计直接冲突

- **PRD §110**：10MB 目标是「≤ 1.0s–1.5s to editable target」——隐含 Typora 侧可对照。
- **PRD §132 任务 17「10 MB」**、**Journey J18「10MB：Open → search → edit → save」**
  ——把 10MB 定为**必须执行**的对照任务。⚠️ **此条引用有误，见文末「更正（2026-09-30）」**
- **PRD §110 同时要求**：「不能只用绝对指标。必须：同机型与 Typora 对照。」

即：PRD 要求「同机型与 Typora 对照」，而该尺寸上 Typora **不存在可比行为**。
按 AGENTS.md「实现与 Spec 冲突 → 先报告冲突，不得擅自裁决」，本 ADR 只登记、不处置。

### 事实三：台账合同文本与该事实不符

`tests/parity/typora-parity-ledger.json` 的 `P0-PERF-001.typoraBehavior` 写的是
「同机、同文档条件下维持可编辑和可导航。」——对 >2MB 不成立。

### 事实四：已有护栏防止把「无基线」当「有基线」用

`run-benchmark.mjs` 的 `ratioOrNA()` 已实现并受护栏保护：基线不渲染该夹具时
**不得相除**，报告输出 `n/a（Typora 拒渲染）`。本轮又补上：
① Typora 侧「基线不适用」提示；② Mellow 大文件模式归属列（阈值 `>5MB` / `>50,000 lines`，
见 PRD §109 与三方一致护栏）；③ hot-open 的判据自证。

## 待决问题

- **Q1**：台账 `P0-PERF-001.typoraBehavior` 应如何更正？（它是「Typora 行为契约」，
  当前文本对 >2MB 为假）
- **Q2**：>2MB 夹具（`5MB.md` 之上、`10MB.md`、`100k-lines.md`）在对照口径中如何处置？
- **Q3**：PRD §132 任务 30 / J18 在 Typora 侧不可执行，如何处置？
  （⚠️ 引用有误 + 该问应拆为两层，见文末「更正（2026-09-30）」）

## 选项

### Q1

| 选项 | 内容 |
|---|---|
| **A1** | 更正为限定式：「同机、同文档条件下维持可编辑和可导航；**Typora 自身对 >2,000,000 字符的文档不渲染，该尺寸无 Typora 行为可比**。」 |
| **A2** | 保持原文不动，仅在 `evidence` 中登记冲突（现状） |

### Q2

| 选项 | 内容 | 后果 |
|---|---|---|
| **B1** | 保留夹具，Typora 列记「不适用」并注明原因（**现状**，`ratioOrNA` 已实现） | 可继续评 Mellow 的绝对指标与「10MB 可编辑」这一能力事实 |
| **B2** | 把 >2MB 夹具从**对照**集合移到**能力观察**集合 | 报告更干净，但失去「同机对照」之外的尺寸连续性 |
| **B3** | 为 >2MB 寻找替代基线（如 VS Code / Obsidian） | 引入第三方，超出 PRD §110「与 Typora 对照」的规定 |

### Q3

| 选项 | 内容 |
|---|---|
| **C1** | 任务 30 的对照尺寸改为 ≤2MB（Typora 可执行），另立「>2MB 能力差异」**非对照**观察项 |
| **C2** | 任务 30 只评 Mellow 绝对指标，Typora 侧记「不适用」并说明原因 |

## 建议（供裁决参考，非结论）

- **Q1 → A1**：合同文本不应包含已知为假的陈述；限定式表述既不削弱 Mellow 的义务，
  也不留下可被误引的假事实。
- **Q2 → B1**：`ratioOrNA` 与报告标注已把风险控制住，改动最小。
- **Q3 → C1**：保留「同尺寸对照」的可比性，同时把「Typora 做不到、Mellow 做得到」
  作为**能力差异**单独记录 —— 这本身就是 PRD §129「10 MB 文档仍然可编辑」的正面证据。

## 更正（2026-09-30）—— 引用核实与 Q3 重新界定

> 按 AGENTS.md 统一规则 16，**不改写本 ADR 原有结论**，只**追加**核实结果。
> 本 ADR 状态仍为 **Proposed**；更正不改变其待决性质，只修正其**事实依据与问题边界**。

### 一、原「事实二」的第 2 条引用不成立（已实跑核对）

原文写「**PRD §132 任务 17「10 MB」**」。逐条核对后，该引用在**三个维度**上都不对：

| 核对项 | 实跑结果 |
|---|---|
| PRD §132 是否含任务清单 | **否**。`docs/product/Mellow-PRD-V1.2-FINAL.md` 的 `# 132. 任务效率 Gate` 正文只有一句「30 个核心 Typora 任务：」+ 四条阈值，**无逐项枚举** |
| 30 项清单在哪里 | `docs/qualification/ux-score-gate-template.md` §二任务表，**30 行**（实跑 `^\|\s*(\d+)\s*\|` 计数 = 30）；master plan §9.5 明写「沿用 `ux-score-gate-template.md` 的 30 项」 |
| 10MB 是第几项 | 模板第 **30** 项（「10MB 文件打开 → 搜索 → 编辑 → 保存」）；记录器 `TASKS` 第 **30** 条（`10 MB 打开、搜索、编辑、保存`）。**第 17 项 = Mermaid**，与 10MB 无关 |

PRD 侧真正把 10MB 定为必须执行的是 **§129「Typora 体验黄金任务」的 J18**
（`## J18 10MB` → `Open → search → edit → save`；§129 开头即「必须全部通过」）。

**教训（与项目既有母题同类）**：把「我们自己写的清单」记成「宪法条款」会让**可自行修正的方法论问题
伪装成宪法级冲突**；反过来也会让人**不敢改本就该改的东西**。引用宪法前先回查宪法原文。

### 二、Q3 应拆为两层（只拆问题，不给结论）

| 层 | 内容 | 性质 |
|---|---|---|
| **Q3a** | 效率 Gate 第 30 项的**对照夹具尺寸**是否改为 ≤2MB（或改为「只评 Mellow 绝对指标」） | **模板/方法论**：PRD §132 未规定夹具尺寸，改之**不违反 §132**；但它改变门禁实际度量的对象，故仍须经本 ADR 登记后才可动 |
| **Q3b** | **§129 J18（10MB 必须全部通过）× §110（必须同机型与 Typora 对照）** 的冲突如何处置 | **宪法级**：§129 与 §110 互斥且基线产品无该尺寸的可比行为，按 AGENTS.md「先报告冲突」只登记 |

原 Q3 把两层混为一问，会导致「要么不敢改模板、要么以为改了模板就等于解决了 J18」。
Q3a 与 Q2 同源（都是「>2MB 在对照口径中如何处置」），裁决时可一并考虑。
