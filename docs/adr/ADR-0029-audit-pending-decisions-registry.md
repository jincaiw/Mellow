# ADR-0029 — 审计中的「未登记裁决项」集中承载 + 登记表为唯一声明处

**Status:** **Proposed**（2026-10-01）—— 待裁决；裁决前不生效

> **本 ADR 的由来**：项目规则是「**待裁决项必须有 ADR 载体**」（AGENTS.md「决策变更」+
> `verify-release-gate.mjs` 的 `PENDING_ADRS`）。但 2026-10-01 逐项复核发现：
> **审计文档里有 6 处「待裁决」标记，而门禁的 `Pending decisions:` 是「无」** ——
> 即这些裁决项**长期没有载体**。
>
> 根因是**护栏只做了单向**：它核对「ADR → 门禁」（已裁决不得退回 Proposed），
> 但**没有核对**「审计里的待裁决项 → 是否有 ADR」。
> 与 §4.10 的教训同源：**两处各自维护同一件事的部分清单，谁都不负责核对全集。**

## 背景：6 处未登记裁决项

| # | 出处 | 裁决问题 | 现状 |
|---|---|---|---|
| Q1 | §4.10.1 | **`settings.open` 在 Windows / Linux 的菜单里没有入口**（Typora 有 File → Preferences）。属**有意差异 D** 还是**缺口**？ | 设计已实现（`Ctrl+,` + 命令面板）且被护栏锁住，但**理由只写在代码注释里**，未进 master-plan 的 D 表 |
| Q2 | §4.4 | **安全验收是否应进入台账**（新增安全域与条目）？ | 治理结构变更，未动 |
| Q3 | §4.5 | **V1.0 发布时是否应把「Apple 凭据缺失」改为硬失败**？ | 发布行为变更，未动 |
| Q4 | §4.39 | **表格 `invalid` 提示**：实现 Mellow 自有提示，还是从 spec 移除？ | 登记为待裁决，未动 |
| Q5 | §4.40 | **`image-workflow-spec` §10 的「上传密钥」**：改写为「不适用」+ 风险说明 / 引入 keychain / UI 提示禁止？ | 登记为待裁决，未动 |
| Q6 | §4.51 | **`tests/visual/actual/*.png` 是否取消 git 跟踪**？（与 README「截图归档/人工评审素材」冲突） | 每跑一次本地视觉套件就弄脏 11 个被跟踪二进制 |

> **Q5 的一手复核（2026-10-01，本轮补）**：**上传路径根本不存凭据** ——
> `App.tsx` 的 `__MELLOW_IMAGE_UPLOAD__` 只传 `httpUrl`（默认 `http://127.0.0.1:36677/upload`，
> PicGo 式**本地端点**）与 `command`（本地 CLI）；扩展的 `keychain`/`process` 权限在 V1 **一律拒绝**。
> 故 Q5 的**前提**（存在需保护的密钥）在本仓**不成立** —— 裁决时应据此重新表述。

## 待决问题

### Q1 — `settings.open` 的 Win/Linux 菜单入口

| 选项 | 内容 | 代价 |
|---|---|---|
| **A1** | **补菜单项**（对齐 Typora 的 File → Preferences） | 需**一手证据**（本机只有 macOS 的 `typora-menu-dump.txt`，Win/Linux 菜单结构**无法本地核实**）；且要同步 master-plan §7.2 的 File 菜单槽位数与护栏 |
| **A2** | **登记为 D（有意差异）**：Win/Linux 走 `Ctrl+,` + 命令面板，不设菜单项 | 只改 D 表与文档；但需确认「确实有意」而非「漏做」 |
| **A3** | 维持现状 + 只把理由从代码注释**搬进** D 表 | 最小改动；若它其实是缺口，则把缺口写成 D = 过度声称 |

### Q2 — 安全验收是否进入台账

**B1** 新增安全域与条目（台账 50 项 → 更多）；**B2** 不新增，改在验收文档中单列一节并说明理由。

### Q3 — Apple 凭据缺失是否硬失败

**C1** 改为 `exit 1`（签名公证成为发布强制前置，会阻断当前无凭据的 pre-release 打包）；
**C2** 保持警告 + 现状护栏（名称不得宣称 `Signed`）。

### Q4 — 表格 `invalid` 提示

**D1** 实现 Mellow 自有提示（与 Typora 文案不同，需登记为 D）；
**D2** 从 spec 移除该要求。

### Q5 — 上传「密钥」的 spec 表述

**E1** 把 spec 改写为「**不适用**（本仓上传不持有凭据）」+ 保留风险说明；
**E2** 引入 keychain（与 V1 的权限拒绝策略冲突）；**E3** UI 提示禁止上传。
（见上文一手复核：前提不成立，**E1 最贴合事实**。）

### Q6 — `tests/visual/actual/*.png` 的跟踪策略

**F1** 取消跟踪（`.gitignore`）+ 把护栏从「文件存在」改为「采集脚本会写出」；
**F2** 保持跟踪 + 每次本地跑完手动回退（现状，本会话已反复执行）。

## 建议（供裁决参考，非结论）

- **Q1 → A2 或 A3**，但**先取证**：A1 需要 Win/Linux 的 Typora 菜单一手证据，本机拿不到；
  在拿到之前**不宜**按「Typora 有、Mellow 没有」断言为缺口。
- **Q5 → E1**：一手复核已证明前提不成立。
- **Q6 → F1**：本会话已**四次**因它产生噪声二进制 diff（每次都要手动回退）；
  代价已实测，收益（人工评审素材）可由「跑采集脚本即生成」替代。
- **Q2 / Q3 / Q4**：均属**发布/治理**层，建议保持现状直到有明确触发条件。

## 后果（若按建议）

- 审计文档新增 **`### 待裁决项登记表（唯一声明处）`**，每行含「出处 / 问题 / 处置 / 载体」；
  **载体**要么指向本 ADR，要么写 `已处置`（并给出证据）。
- 门禁 `PENDING_ADRS` 纳入本 ADR；`Pending decisions:` 行随之可见。
- **新增护栏**（`verify-release-gate.mjs`）：登记表必须存在，且**每一行的「载体」必须可解析**
  （指向存在的 ADR 文件，或字面量 `已处置`）—— 防「登记表指向不存在的 ADR」。
  > **范围限制（如实声明）**：本护栏**不能**自动发现「审计里新出现了一个 `待裁决` 标记但没登记」
  > —— 那需要理解自然语言。它只能保证**已登记的**部分自洽。要补上这一半，需给标记定一个
  > 机器可读的写法（如统一 `<!-- PENDING: id -->`），属后续工作。
