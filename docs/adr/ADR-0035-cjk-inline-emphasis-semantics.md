# ADR-0035 — 行内强调的**渲染语义**：`**` 紧贴全角标点时，**对齐 Typora** 还是**保持 CommonMark**？

**Status:** **Proposed**（2026-10-10）—— 待裁决。

> **本 ADR 为什么是 Proposed**：它改的是**同一份 Markdown 在 Mellow 与 Typora 里看起来不同** ——
> 属**用户可见的渲染结果**，不是审计派生出来的死代码清理。
> 方案自己早已写下「**不能把 Typora 行为自动视作 CommonMark 正确性**」
> （`docs/plans/markdown-syntax-demo-parity-validation-plan.md` 第 77 行）
> ⇒ 这是一个**需要裁决的取舍**，不是可以自裁的缺陷修复。
> **本 ADR 只做两件事**：① 把这条差异**从散文搬进机器可读的登记处**；
> ② 给出**逐项事实与建议**，使裁决成本降到「看一眼就能定」。

## 背景：这条差异是什么（**一手证据**）

**Mellow 侧两条渲染路径都用 CommonMark 语义**：

- **预览**：vendored `CoreEditor` 的 live-markdown 由 `@lezer/markdown` 解析；
- **导出（HTML / PDF）**：`packages/export/src/html/markdown.ts` 用 `markdown-it` + 插件。

**Typora 侧不是 CommonMark**。其 `appsrc/main.js` 里的行内规则是
（**一手证据，本机 Typora 1.14.9 / build 7785**）：

```
strong: /^__(?=\S)([\s\S]*?\S)__(?!_)|^\*\*(?=\S)([\s\S]*?\S)\*\*(?!\*)/
em:     /^_(?=\S)([\s\S]*?\S)_(?!_)|^\*(?=\S)([\s\S]*?\S)\*(?!\*)/
```

且 `ue.gfm = ue.normal` ⇒ **GFM 预设用的就是这两条**。
⇒ Typora 的强调**只要求「定界符内侧紧邻非空白」**，**完全没有** CommonMark 的
left-/right-flanking（标点相邻）规则，也没有 CommonMark 规则 9（长度和不得为 3 的倍数）。

**实测（三条独立通道，均可复现）**：

| 输入 | Typora（marked 正则） | Mellow 预览（`@lezer/markdown`） | Mellow 导出（`markdown-it`） |
|---|---|---|---|
| `中文**粗体**中文` | 加粗 | 加粗 | 加粗 |
| `这是**「必须」**的` | **加粗** | **不加粗**（无 `StrongEmphasis` 节点） | **不加粗**（HTML 里是字面 `**`） |
| `**「引文」**`（行首 / 行尾） | 加粗 | 加粗 | 加粗 |
| `这是 **「必须」** 的`（两侧留空格） | 加粗 | 加粗 | 加粗 |

**失效边界**：`**` 的**内侧**紧贴全角标点（`「」（）【】《》『』“”：；，。` 等）
**且外侧紧贴汉字**。只要有一侧不是这个组合（行首 / 行尾、外侧留空格、内侧是汉字），
三条路径**都**正常。

**这不是边角情形**：`这是**「必须」**的` 是中文写作里的**常见写法** ——
本仓自己的文档里就实测有 **87 处**（审计 §4.246 因此落判据 ㊵）。

## 为什么它不是「已闭环」

台账 `P0-MARKDOWN-002`（capability = 「强调、链接、行内代码」，`status = AUTO`，
`requiredEvidence = unit / macos / windows-ci / linux-ci`，**不含 `ux-gate`**）⇒ **门禁视为闭环**。
但该条的 `typoraBehavior` 写的是「行内 Markdown 在**输入、选区与快捷键操作**下稳定显示和回写」，
`mellowTarget` 写的是「**格式命令**不损坏选择、IME 或原有空白」
—— **两句话说的都是「命令行为」，不是「解析器对同一段源文本的语义」**。

⇒ 本差异**不在任何台账条目的覆盖范围内**（D 表、PRD、偏好矩阵亦无登记，已逐处实测）。

## Q1 — `**` 紧贴全角标点时，是否改为**渲染成加粗**（对齐 Typora、偏离 CommonMark）？

**选项**

- **A1 — 对齐 Typora（预览 + 导出都改）**：两条路径都放宽为「内侧非空白即可」。
  - 代价：偏离 CommonMark 与 GitHub 渲染；`markdown-it` 需自定义 inline rule（或换解析器）；
    **预览侧的改动落在 vendored `CoreEditor`**（`@lezer/markdown`），而 vendored 树的改动有额外成本
    （`UPSTREAM.md` 由 sha256 清单离线校验，改完必须登记）。
  - 收益：中文用户**最常见的写法**在 Mellow 里与 Typora 一致。
- **A2 — 只改导出（预览不动）**：导出对齐 Typora，预览保持 CommonMark。
  - ⚠️ **不推荐**：会造成「**同一份文档在预览里与导出件里长得不一样**」——
    这违反 PRD 的「可预测输出（Source Fidelity）」精神，属**新增**一类不一致。
- **A3 — 保持 CommonMark（现状），登记为有意差异**：把本条登记进 **D 表**并写明依据
    （「CommonMark 是标准；Typora 在此处偏离标准」）。
  - 代价：中文用户继续看到字面 `**`。
  - ⚠️ 若选此项，**必须同时**给出「用户如何自救」的说明（在定界符外侧留空格、或把引号移出加粗），
    否则「有意差异」与「没发现」在用户眼里没有区别。

**建议 = A1**（若改动能控制在预览侧的**装饰层**而不动 vendored 解析器，则 A1 的代价显著下降）。

> ⚠️ **本 ADR 不实施任何改动**：改的是**用户可见的渲染结果**，属产品决策。
